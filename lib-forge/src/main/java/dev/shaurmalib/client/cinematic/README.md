# dev.shaurmalib.client.cinematic — Cinematic Timeline Engine

Доповнення до плану `shaurma-lib` (розділ 3, п. 3.4 частково —
`AnimatedCountdownSystem`/`WorldTintOverlay` вже описані як окремі
overlay-рушії, але сам **сценарний оркестратор**, що вирішує "в якому
порядку і коли" ці оверлеї/звуки/камера вмикаються, у плані описаний
не був — саме цей пробіл і закриває модуль нижче).

## Що замінює

`SCCinematicSequencer.java` (533 рядки, `snipers_shaurma`) —
захардкоджений `enum State` + `switch` + окрема функція
`applyPingCompensation()`, що вручну дублювала кожен крок стейт-машини
ще раз (6 копіпаст-блоків "виставити прапорці, що вже пройдено").
Розгалуження SC/SR/SCN трималось на `if ("scn".equals(modeId))`,
розкиданому по 5+ місцях усередині методів `tickHold`/`tickWhitenIn`/
`tickWhitenOut`/`tickGoShow`/`applyPingCompensation`.

## Чому це "як у снайперах, тільки гнучкіше"

- `CinePresets.classic(...)` і `CinePresets.scn(...)` відтворюють
  **точно ту саму** послідовність кроків і таймінги (`Timings.defaults()`
  = HOLD 2000мс / WHITEN_IN 1000мс / COUNTDOWN 3000мс / WHITEN_OUT
  500мс / GO_SHOW 800мс — числа взяті буквально з оригінального
  класу), тобто гравець не побачить жодної різниці в поведінці.
- Різниця SC/SR/SCN — не `if` усередині рушія, а різний набір кроків,
  побудований у моді через `CineHooks`. Режим друга (maniac) описує
  власну кінематику своїм `CineHooks`-імплементатором і власним
  списком `CineStep`, не займаючи жодного розгалуження в бібліотеці.
- Ping-compensation (`begin(offsetMs)` + `catchUpIfNeeded()`) — один
  цикл замість шести ручних копій. Додавання нового кроку в
  послідовність автоматично отримує коректну поведінку "пізнього
  приєднання", без окремого редагування функції ping-compensation.
- `signal(stepId)` узагальнює `onServerStartCountdown()` на будь-який
  крок таймлайну, а не лише на перехід MISSION_OVERLAY→COUNTDOWN.

## Чому це знадобиться для реплею (і не лише кінематики старту матчу)

`CineRecording` — це не "фіча для одного випадку", а сама причина,
чому цей модуль вартий окремого виділення в бібліотеку зараз, а не
пізніше:

- `CineTimeline` вже структурно розділяє **послідовність немовних
  подій сцени** (overlay/звук/камера-тригер, з точним часом) від
  **рендеру** цих подій (`CineHooks`, overlay-класи). Це саме той
  поділ, що потрібен для реплею: запис = список `(timestampMs, stepId)`
  ("що і коли сталось"), відтворення = той самий список кроків,
  програний через `recording.replay(steps, replayContext)`.
- Це узагальнюється на будь-яку сцену, не лише "старт матчу":
  end-game статистика (`EndGameCameraManager`), катсцена нагородження,
  вступна кінематика нової карти — усе, що зараз у снайперах було б
  ще одним окремим `XxxSequencer`-класом з власним `enum State`, тепер
  — просто новий набір `CineStep` і `CineHooks`.
- Для "реплею карти" в іншому моді: мод пише свій `CineRecording` під
  час гри (кожен важливий момент сцени — виклик кроку), зберігає його
  на диск (формат серіалізації — відповідальність мода, `entries()`
  віддає прості `(long, String)` записи). При перегляді реплею
  `CineRecording.replay(steps, replayContext)` підміняє тривалості
  кроків на записані (а не оригінальні `durationMs`) — тому реплей
  відтворює РЕАЛЬНИЙ хід подій матчу (включно з можливими затримками
  через ping чи ручне втручання), а не ідеалізовану "як мало бути"
  послідовність. Камера під час реплею прив'язується так само, як і в
  живій грі — `CineHooks`-реалізація мода викликає
  `CameraPresets.xxx(...).activate()` (з уже наявного `camera`-модуля,
  напр. `PathMotion`/`FollowMotion`) усередині свого `onXxx()`-методу;
  два модулі (`camera` + `cinematic`) складаються без залежності одне
  на одного напряму.

## Місце в плані впровадження (розділ 5)

Логічно додається в **Етап 2** (клієнтський UI-рушій), одразу після
кроку 10 (`client.overlay`/`OverlayEngine`) — `CineHooks`-реалізації
природно викликають саме overlay-класи з цього кроку. Перед
`dev.shaurmalib.radio` (крок 22 в оригінальному плані) сенсу немає,
бо радіо-репліки самі можуть бути ще одним видом кʼю всередині
таймлайну (`RadioDialogManager.trigger(...)` викликаний з
`CineHooks`-методу), а не навпаки.

Міграція snipers (Етап 6): `SCCinematicSequencer` замінюється на
`CinePresets.classic/scn/srMissionOnly` + власний `SnipersCineHooks`
клас, що робить рівно ті виклики, які раніше були прямо в тілі
сиквенсера. Регресійний чек-лист — усі 3 послідовності (SC, SR, SCN) +
ping-compensation (приєднання під час активної кінематики) окремо,
той самий рівень обережності, що вже передбачений планом для інших
"важких" систем.
